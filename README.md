# VPS Orchestrator

Self-hosted оркестратор VPS с VLESS REALITY и стабильными Mihomo/Clash-подписками. Один Go-бинарник содержит веб-интерфейс и весь комплект развёртывания. Отдельного агента и управляющего HTTP API на VPS нет: установка, чтение конфигурации и управление пользователями выполняются по SSH.

## Что он делает

- Устанавливает Xray, Nginx с сайтом-заглушкой и self-steal, сертификат Let's Encrypt через DuckDNS, firewall и SSH-доступ по ключу. Поддерживаются чистые Ubuntu 22.04, 24.04 и 26.04.
- Создаёт профили пользователей и выдаёт постоянную ссылку `/subscribe/{token}`. Каждому профилю можно назначить все серверы, включая будущие, или только выбранные.
- Согласует фактических клиентов Xray с назначениями. Список пользователей хранится в конфигурации Xray и переживает перезапуск VPS без скрипта синхронизации.
- Формирует конфигурацию Mihomo/Clash с fallback между доступными серверами и DIRECT-правилами для российских доменов и приложений. Подписка обновляется клиентом каждые 6 часов.

Изменение состава пользователей вызывает короткий перезапуск Xray только на затронутом сервере. Повторная синхронизация без изменений проверяет службы и не перезапускает их.

## Запуск в Docker

Публичный образ: `drun555/vps-orchestrator`, платформы `linux/amd64` и `linux/arm64`.

Скачайте `compose.yaml` из репозитория и запустите:

```sh
docker compose up -d
docker compose logs orchestrator
```

Откройте панель через свой HTTPS reverse proxy (или локально `http://localhost:42345`). Мастер первого запуска попросит код из журнала, публичный URL панели, email для сертификатов и пароль администратора. Общий токен DuckDNS можно добавить сразу или позже в «Настройках». `.env` для этого не требуется. Код действует только до завершения настройки.

Compose публикует порт на `127.0.0.1:42345`. Существующая схема HTTPS reverse proxy сохраняется: `/subscribe/*` и `/mihomo/*` должны оставаться доступны VPN-клиентам. Панель использует встроенный пароль и cookie-сессию на 24 часа. Если в настройках указан HTTPS URL, браузер должен открывать панель по HTTPS. Изменение пароля завершает старые сессии.

При обновлении уже настроенной установки с `BASE_URL` и `CERTBOT_EMAIL` сохраняется прежняя авторизация на reverse proxy. Встроенный пароль можно включить в «Настройках», не меняя ссылки подписок.

Контейнер работает с UID/GID `10001:10001`, не требует privileged-режима или Docker socket. Данные находятся в volume `orchestrator-data`, каталог `/data`. При использовании bind mount предоставьте этому UID доступ к каталогу. `master.json` содержит SSH-ключи и токены, поэтому резервируйте его как секрет. Файлы состояния не включаются в образ.

Для фиксированной версии укажите, например, `drun555/vps-orchestrator:2.2.0` вместо `latest`. Обновление контейнера не затрагивает данные volume.

## Запуск бинарника

```sh
go build -o vps-reality-master .
./vps-reality-master
```

`./scripts/build.sh` собирает Linux-бинарники для amd64, arm64, armv7, mips и mipsle (softfloat). `register-initd.sh` сохраняет поддержку Entware/SysV для запуска с конфигурацией и состоянием рядом с бинарником.

Переменные окружения имеют приоритет над `.env` рядом с исполняемым файлом. `.env` необязателен. URL и email из окружения или `.env` имеют приоритет над настройками браузера и показаны в форме как поля только для чтения. Чтобы управлять ими из браузера, удалите эти значения из окружения и `.env`.

| Параметр | Значение |
| --- | --- |
| `BASE_URL` | Публичный HTTP(S) URL; без значения настраивается в браузере |
| `CERTBOT_EMAIL` | Email для Let's Encrypt; без значения настраивается в браузере |
| `LISTEN_ADDRESS` | По умолчанию `0.0.0.0` |
| `PORT` | По умолчанию `42345` |
| `DATA_DIR` | Каталог состояния; по умолчанию рядом с бинарником, в Docker `/data` |

Настройка `SLAVE_SETUP_URL` больше не используется. Все установочные файлы встроены в бинарник; VPS не скачивает репозиторий оркестратора. Пакеты Ubuntu и Xray устанавливаются из внешних источников, как и раньше.

## Добавление VPS

1. Один раз создайте поддомен в [DuckDNS](https://www.duckdns.org). Его [официальный API](https://www.duckdns.org/spec.jsp) позволяет обновлять существующие имена, но не документирует регистрацию новых. Оркестратор автоматически привяжет выбранное имя к исходящему IPv4 VPS. Для этого VPS нужен доступ в интернет по IPv4.
2. В «Настройках» сохраните токен DuckDNS. Если все существующие VPS используют один токен, он автоматически импортируется как общий. Токен никогда не возвращается браузеру; пустое поле сохраняет его. Новый общий токен используется для новых и незавершённых установок. На уже работающих VPS токены Certbot автоматически не заменяются.
3. Нажмите «Добавить сервер», укажите имя, SSH-адрес, поддомен и root-пароль. Оркестратор создаст отдельный ключ Ed25519, сохранит его до изменений сервера, добавит публичный ключ и проверит новое подключение. Root-пароль не сохраняется. После установки вход по паролю отключается; существующие ключи владельца остаются.
4. Если VPS уже доступен по ключу, выключите вход по паролю и выберите файл приватного ключа. Публичная часть определяется автоматически. Для другого аккаунта DuckDNS можно указать отдельный токен в форме сервера.

Прерванная установка остаётся в списке серверов. «Продолжить установку» использует сохранённый SSH fingerprint, ключ и контрольные точки на VPS. Пароль потребуется повторно только если ключ ещё не установлен. Завершённые этапы пропускаются, REALITY-ключи и существующие пользователи не пересоздаются. Общая синхронизация пропускает незавершённые установки. Удаление и повторная установка не нужны для исправления токена, временной ошибки сети или Certbot.

Контрольные точки находятся в `/opt/vps-reality/runtime/setup-stages/`; `setup-owner` связывает каталог с конкретной записью оркестратора. Установщик откажется перезаписывать чужую или старую установку без этой метки. Для действующих серверов используется обычная синхронизация, а не повторная установка.

API продолжения: `POST /api/servers/{id}/resume` с `{}` или `{"password":"..."}`; ответ содержит `job_id`. Настройки доступны через `GET/PUT /api/settings`, вход — `POST /api/login`. Подписки не требуют сессии администратора.

## Шаблоны сайта-заглушки

Стандартная страница — `deploy/index.html` (Selfhosted File Hosting). Дополнительные варианты в том же стиле:

- `deploy/templates/syncthing.html` — Private Syncthing Server, синхронизация доверенных устройств.
- `deploy/templates/backup-vault.html` — Private Backup Vault, резервные копии, архивы и восстановление больших объёмов данных.
- `deploy/templates/minecraft-worlds.html` — Worldkeep, резервные копии миров Minecraft; отдельный дизайн с пиксельным пейзажем.

Это самостоятельные HTML-страницы без внешних зависимостей; они включаются в комплект развёртывания. Выберите вариант в поле «Сайт-заглушка» при добавлении VPS. Выбор сохраняется в состоянии сервера и используется при продолжении прерванной установки. По умолчанию используется Selfhosted File Hosting; существующие VPS не меняются. API `POST /api/servers` принимает необязательное поле `site_template`: `file-hosting`, `syncthing`, `backup-vault` или `minecraft-worlds`. Неизвестные значения отклоняются. На работающем VPS можно заменить только `/opt/vps-reality/index.html`; перезапуск служб не требуется. Шаблоны не устанавливают Syncthing или сервис резервного копирования.

## Назначение серверов

В форме пользователя доступны режимы:

- **Все, включая будущие** — автоматически получает доступ к новым VPS.
- **Только выбранные** — доступ только к отмеченным серверам. Пустой выбор отключает все серверы.

Редактирование назначения сохраняет ссылку подписки. Исключённый сервер исчезает из подписки сразу после сохранения назначения. Реальный доступ по ранее выданным реквизитам прекращается после успешного применения на VPS. Если VPS недоступен, отображается «отзыв не завершён»; нажмите повторную или полную синхронизацию после восстановления SSH.

Полная синхронизация авторитетна: удаляет лишних клиентов, дубликаты и доступ пользователей, удалённых из оркестратора. Фоновая автоматическая синхронизация не запускается.

HTTP API использует существующие фоновые задачи и SSE-журнал:

```json
POST /api/users
{"email":"Иван","server_mode":"selected","server_ids":["server-id"]}

PATCH /api/users/{id}
{"server_mode":"all","server_ids":[]}
```

Ответ — `202` с `job_id`. При создании без `server_mode` используется `all`; при редактировании режим обязателен. Неизвестные ID отклоняются. `/api/overview` возвращает назначения и статусы без SSH-секретов. Пустой proxy-provider возвращает `proxies: []`.

## Обновление старой установки

1. Сделайте резервную копию старого бинарника и `master.json`. Остановите старый оркестратор; два экземпляра не должны одновременно управлять одним набором VPS.
2. Замените бинарник или перенесите состояние в Docker volume. При первом запуске формат состояния обновится с v1 до v2, рядом появится `master.json.v1.bak`. Существующие пользователи получают режим «Все»; их токены и SSH-ключи сохраняются.
3. Запустите синхронизацию. Первая операция управления пользователями на каждом старом VPS выполнит его миграцию. Сам запуск оркестратора удалённые серверы не меняет.
4. Проверьте журнал и статусы. При ошибке исправьте SSH-доступ или причину отказа службы и повторите синхронизацию.

Миграция читает старый `runtime/clients.json`, сохраняет UUID и REALITY-ключи, переносит пользователей в конфиг Xray, убирает CGI-маршруты и `ExecStartPost` восстановления пользователей. Certbot hooks и сайт-заглушка сохраняются. Общие пакеты и службы других приложений не удаляются.

До применения конфиг проверяется Xray; перед изменением создаются резервные копии. При ошибке запуска восстанавливается предыдущая конфигурация. После обрыва SSH незавершённая транзакция восстанавливается при следующей операции. На VPS исходные конфиги остаются в `/opt/vps-reality/runtime/pre-ssh-migration/`, резервная копия последней транзакции — в `orchestrator-transaction/`. Не откатывайте только master-бинарник на HTTP-версию после миграции VPS: потребуется также восстановить старые управляющие файлы VPS.

SSH fingerprint принимается при первичной установке и проверяется при последующем управлении. Смена host key требует проверки администратором; автоматического обхода проверки нет.

## Сборка и публикация

CI запускает тесты, race detector, shell-проверки и сборку обычных бинарников. Docker workflow проверяет PR без публикации. Версионный тег `vMAJOR.MINOR.PATCH` публикует соответствующий Docker-тег и `latest`; prerelease публикует только собственный тег. Ручной запуск принимает существующий версионный Git-тег.

Для публикации в namespace `drun555` нужен Actions secret `DOCKERHUB_TOKEN` с правом Read & Write. Токены не передаются в Docker build.

```sh
go test ./...
go test -race ./...
bash -n deploy/setup.sh deploy/uninstall.sh deploy/hooks/*.sh
./scripts/build.sh
docker build -t vps-orchestrator:test .
```

Опциональная проверка действующих серверов: `VPS_LIVE_STATE=/secure/master.json go test -run TestLiveServerAcceptance -v`. Она только читает данные. Для миграции одного конкретного сервера дополнительно задайте `VPS_LIVE_MIGRATE` равным его точному ID. Этот тест не выполняет миграцию без явного параметра и не запускается в обычном CI.
